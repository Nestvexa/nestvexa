# Security checkpoint review — 2026-10-26

Scope: source review of the implemented Live request admission, generated Nest routes, state restoration, protocol/store, browser response validation and DOM morph boundaries. This is a scoped engineering review, not an independent penetration test or a release security approval.

The reviewed implementation validates browser envelopes as bounded plain JSON, rejects prototype keys/accessors and unsupported state types, binds opaque state tokens to host identity, and checks revision/lock state before invoking effects. Generated routes retain Nest metadata and resolve component providers through the actual request context. Host body parsing limits, authoritative session/tenant resolution, CSRF token generation, permission revocation and business transaction/idempotency controls remain explicit host responsibilities.

## Concrete finding

The initial fragment guard compared `element.tagName` against uppercase HTML names. SVG element names are lowercase, so an SVG `script` node passed the advertised active-element rejection. SVG animation can also modify URL attributes after a static attribute inspection. This was a gap in the browser's defense in depth; the adapter already requires trusted templates, escaped data and a restrictive CSP, and does not claim general HTML sanitization. The review did not establish an untrusted-data-to-script execution chain through the supported escaped HBS rendering path.

The coordinating engineer implemented an explicit HTML-only Live fragment capability for this initial runtime. Foreign SVG/MathML markup is rejected before morphing until a separately reviewed adapter safely supports it. The regression test uses Chromium's actual HTML parser and the compiled client module, covering SVG script, animation, MathML, inline handlers, obfuscated unsafe URLs and safe HTML acceptance. It also verifies that cross-origin endpoint markers do not reach the supplied transport. Both browser security tests passed in the focused run after the root fix.

A second consistency gap was reproduced in initial rendering: update responses were capped at1MiB but initial mounts had no equivalent rendered-HTML cap. A real HBS adapter with an allowed larger source template produced1MiB+1 HTML and allocated a state token. The coordinating engineer added the same413 rejection to rendering before token allocation. The [initial mount regression](../../tests/live-security.test.ts) initially failed, then passed after that source fix, confirming that oversized initial HTML creates no state token.

See [client security tests](../../tests/client-security.test.ts). Live/client builds, test TypeScript compilation, focused ESLint and all three review regression tests passed locally on Windows/Node24.13.0. These tests launch Chromium, so contributors and CI must install its Playwright binary before running the default or security suite. Root aggregate checks must refresh the shared test report after focused runs. No P0/P1 exploit was demonstrated in this limited review. Full master-spec security, mutation/fuzz coverage, all supported browser behavior and distributed/session fault testing remain release gates.
