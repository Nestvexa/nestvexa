# Internationalization and RTL

`@nestvexa/i18n` is an optional package. It adds locale negotiation, translated
catalogs, `Intl` formatting and right-to-left layout support to HBS MVC pages and
Live components without touching the default `nestvexa` install. API details live in
the [package README](../../packages/i18n/README.md); this guide walks through a
complete English + Arabic setup like the one in
[examples/admin-i18n](../../examples/admin-i18n).

## 1. Catalogs

Lay catalogs out as `locales/<locale>/<namespace>.json`:

```text
locales/
  en/common.json      {"title": "Products", "save": "Save"}
  en/validation.json  {"nameShort": "Enter at least {min, number} characters."}
  ar/common.json      {"title": "المنتجات", "save": "حفظ"}
  ar/validation.json  {"nameShort": "أدخل {min, number} أحرف على الأقل."}
```

Plurals use `Intl.PluralRules`, so Arabic gets all six categories:

```json
{
  "count": "{count, plural, zero {لا توجد منتجات} one {منتج واحد} two {منتجان} few {# منتجات} many {# منتجًا} other {# منتج}}"
}
```

Load them for the allowlisted locales only; anything else in the directory is
never read:

```ts
const catalogs = await loadCatalogs(
  fileURLToPath(new URL('../locales', import.meta.url)),
  {
    locales: ['en', 'ar'],
  },
);
```

## 2. Configure the module

```ts
I18nModule.forRoot({
  locales: ['en', { code: 'ar', label: 'العربية' }],
  defaultLocale: 'en',
  timeZone: 'UTC', // explicit policy; choose the business zone deliberately
  catalogs,
});
```

The time zone is required. Dates render in that zone everywhere unless a call
passes an explicit, validated `timeZone` (for example a per-user preference that
your application stores and validates itself).

Register the helpers on the umbrella's engine before `configureNestvexa`:

```ts
const app = await NestFactory.create(AppModule);
app.get(HbsEngine).registerHelpers(app.get(I18n).helpers());
await configureNestvexa(app);
```

## 3. Layout: `lang` and `dir`

Apply `LocaleViewInterceptor` to rendered routes. It adds `i18n` to the model and
sets `Content-Language` plus `Vary: Accept-Language, Cookie`:

```hbs
<html lang='{{lang}}' dir='{{dir}}'>
  <head><title>{{t 'title'}}</title></head>
  <body>{{body}}</body>
</html>
```

Setting `dir` on `<html>` flips the inline axis for the whole document: text
alignment, table column order, flex/grid direction and form controls follow it.
Write CSS with logical properties so the same stylesheet serves both directions:

```css
.toolbar {
  padding-inline-start: 1rem; /* not padding-left */
  border-inline-end: 1px solid; /* not border-right */
  text-align: start; /* not left */
}
.chevron:dir(rtl) {
  transform: scaleX(-1); /* mirror directional icons only */
}
```

Do not mirror logos, media controls, numbers or code. Keep user-provided text in
`<bdi>` or with `dir="auto"` when its direction is unknown (names, product titles).

## 4. Switching language without JavaScript

Negotiation precedence is `?lang=` → `nv-locale` cookie → `Accept-Language` →
default; unlisted values are skipped. A progressive-enhancement switch is a normal
form post that sets the cookie and redirects back:

```hbs
<form method='post' action='/locale'>
  <input type='hidden' name='_csrf' value='{{csrf}}' />
  <button name='locale' value='en' lang='en'>English</button>
  <button name='locale' value='ar' lang='ar'>العربية</button>
</form>
```

```ts
@Post('locale')
@Redirect('/', 303)
switchLocale(@Body('locale') locale: unknown, @Res({ passthrough: true }) response: Response) {
  const chosen = this.i18n.match(locale);
  if (!chosen) throw new BadRequestException();
  response.setHeader('Set-Cookie', this.i18n.localeCookie(chosen, { secure: true }));
}
```

Protect this route with the same CSRF policy as other forms. Redirect to a fixed
or allowlisted path, never to a `Referer`/query value.

## 5. Live components and translated validation

Expose the negotiated view as a `@Computed` so it is re-derived on every request and
never enters writable or locked state:

```ts
constructor(
  @Inject(I18n) private readonly translations: I18n,
  @Inject(REQUEST) private readonly request: object,
) {}
@Computed() get i18n() {
  return this.translations.forRequest(this.request).view;
}
@Action() save(): void {
  const t = this.translations.forRequest(this.request);
  if (this.name.trim().length < 2) {
    this.nameError = t.t('validation:nameShort', { min: 2 });
    return;
  }
  flashLive(this, t.t('products:created', { name: this.name }));
}
```

Templates use `{{t 'common:save'}}` and `{{formatCurrency price 'SAR'}}` exactly like
MVC pages because the helpers read `i18n.locale` from the root model. Validation
messages stored in state stay in the language they were produced in until the next
action re-validates; re-run validation (or store message keys and translate in the
template) if a mid-form language switch must re-translate errors immediately.

Keep locale out of `authorize(identity, component, action)`: permissions must not
change with language. Never derive realtime channel names, snapshot keys or tenant
identity from the locale or direction.

## 6. Cache keys

- Full pages: shared caches must vary on locale. `Vary: Accept-Language, Cookie`
  is conservative; if you cache by a normalized key, use the negotiated locale.
- Fragments: include `locale` and, if it can vary, `timeZone` in the key.
- Live snapshots: locale-free when the locale is a `@Computed`.
- Never cache an HTML response for one locale under another's key; the
  `Content-Language` header helps detect mistakes in CDN logs.

## 7. Extraction workflow

Run the extractor in CI to catch missing translations:

```sh
pnpm exec nestvexa-i18n-extract src --catalogs locales --locales en,ar
```

It scans `.hbs` and `.ts` files for literal keys (`{{t "k"}}`, `{{tHtml "k"}}`,
`(t "k")`, `t('k')`, `i18n.t(locale, 'k')`), reports dynamic keys with file and line,
prints deterministic JSON, and exits `1` when any locale lacks a key. Commit the
`--out` file if you want key changes to show up in code review.

## Limits

ICU subset only (no `offset`, `choice`, skeletons or rich-text functions); output
depends on the runtime's CLDR data; catalogs load at startup; no automatic client
catalog hydration. See the package README for the full list.
