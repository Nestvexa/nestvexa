# ADR 0002: Versioned Live requests with opaque server-state references

Date: 2026-10-25; model synchronization amendment2026-10-26. Status: **accepted initial protocol, partially implemented; full acceptance pending**. The implementation uses opaque server-state references; signed browser snapshots and distributed stores remain outside the current slice.

## Decision and boundary

The initial Live transport uses a versioned JSON envelope and opaque, cryptographically random server-state reference. A registered generated route identifies the component/action; its body carries the reference, expected revision, request ID and bounded public updates/input. Responses include the stable component instance ID and next revision. The browser may not choose a class, provider token, template filename, module import or method outside the registration table. Initial rendering is performed through an ordinary authorized Nest route.

The server stores the component definition reference, allowlisted public state, expiry, revision and host-derived owner binding. Binding includes session, principal and tenant; none is taken from request JSON. An anonymous flow needs an explicit host-generated anonymous session identity, rather than an empty owner shared by visitors. The reference is a capability secret in addition to these checks: do not log it, put it in URLs or share rendered private component markup between users. Store references do not make state rendered into HTML confidential.

The protocol's first implementation must reject unsupported protocol majors, unknown fields, unsafe keys, nonfinite numbers, excessive nesting/bytes and invalid action/state paths. Every mutation requires host-verified identity, CSRF, origin policy, content type, payload limits and authorization. Missing policy configuration fails closed. Read/refresh operations still require ownership and authorization; a refresh is not a way to bypass action restrictions.

Dispatch uses explicitly generated Nest controller methods and public decorators, with component/action metadata copied deliberately. Nest runs guards, pipes, interceptors and filters; the framework does not construct guards manually. The scope and ordering proof described in [ADR 0003](0003-nest-execution-pipeline.md) is a blocking prerequisite. Generated handler identity is distinct from the original component method; metadata-sensitive extensions must be tested and documented rather than assumed compatible.

Model synchronization has one fixed generated `POST <endpoint>/<component>/_sync` route, separate from registered action methods. The authorization policy must explicitly allow `$sync` for this component and current identity. Synchronization follows the same trust checks and revision transaction as actions. It executes component/global Nest policies, interceptors and filters, without borrowing any action method's metadata or calling an action. Component/global guards or `authorize` must enforce every-write policies. `input` must be absent or null. Its lifecycle is `hydrate → apply writable updates → dehydrate → render`, without action hooks.

Client model modes are deferred by default; live, blur/change, decimal/boolean casts and bounded debounce/leading throttle configure when a synchronization request is queued. No directive is executable code. IME intermediate input is held locally, and invalid conversion blocks requests rather than sending an earlier valid value. Timers are canceled on configuration/ownership changes and disposal. These client rules improve predictable transport behavior but never grant server write authority.

Writable-state kind/allowlist checks and optional pure `State({writable:true, validate})` callbacks run before the transaction and before component hooks. Validators receive detached immutable JSON and must return `true`. Rejected updates return422 with the snapshot/revision still usable. An atomic transaction revision check after validation prevents a successful validator from admitting stale state. Failures after component execution begins still invalidate the token because external effects may be uncertain.

## Alternatives, cost and failures

Signed browser snapshots were rejected for the initial slice: they increase canonicalization/key-rotation surface and still require replay and owner controls. They may become a separately tested capability. A stateless reference without revision storage was rejected because it cannot safely coordinate mutations. Arbitrary RPC dispatch was rejected because it broadens the exposure boundary.

The cost is server storage, expiry cleanup and an explicit scale-out store contract. Memory-store deployments are single-process and lose components on restart. Unknown, expired, revoked or conflicting references return stable public errors with no state disclosure. Actions with uncertain effects must not be transparently retried; see [ADR 0005](0005-state-and-concurrency.md).

Requiring an ordinary action for every live field edit was rejected: it couples synchronization to application method names and action hooks. Reusing an arbitrary action's method guard was also rejected because no unambiguous method applies. The fixed synchronization route adds an explicit policy surface and rate-limit cost. Applications may deny `$sync` and use deferred fields submitted through authorized actions. Pure validation before reservation adds a race window, resolved by the transaction's revision check rather than by treating validation as a lock.
