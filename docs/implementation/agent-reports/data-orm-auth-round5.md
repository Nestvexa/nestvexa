# Round 5 report: database and authentication interoperability (DATA-014 to DATA-018)

Branch `r5-data-orm-auth`. Spec section 15.3. No package under `packages/`
was changed; everything is examples, tests and docs. `packages/cli`,
`packages/core` and the umbrella are untouched.

## DATA-014: Prisma, TypeORM and Drizzle examples

**Implemented.** Three small Nest (Express) examples keep notes in SQLite and
read/write them through an HBS page (MVC), a Live component (`note-board`,
async computed reads, `add` action) and a server-action group (`notes/list`,
`notes/add`). `src/app.ts`, `src/notes.ts` and the views are byte-identical
across the three; only `src/database.ts` (plus ORM schema files) differs.

| Example                | Stack (exact versions)                                                                 |
| ---------------------- | -------------------------------------------------------------------------------------- |
| `examples/orm-prisma`  | `prisma` / `@prisma/client` / `@prisma/adapter-libsql` 7.10.1, `@libsql/client` 0.18.0 |
| `examples/orm-typeorm` | `typeorm` 1.1.2, `sql.js` 1.15.2 (WebAssembly SQLite)                                  |
| `examples/orm-drizzle` | `drizzle-orm` 0.45.4, `@libsql/client` 0.18.0, `drizzle-kit` 0.31.11 (dev)             |

- No native module with an install script is needed: libSQL ships prebuilt
  binaries through optional dependencies, sql.js is WebAssembly.
- Prisma's generate step is part of the example build (`prisma generate && tsc`,
  same on Windows and Linux) and writes to `examples/orm-prisma/src/generated`
  (git-ignored, excluded from ESLint and Prettier). Prisma 7 needs no
  downloaded engine for `generate`; `pnpm-workspace.yaml` lists `prisma`,
  `@prisma/engines` (and `argon2`, see below) under `ignoredBuiltDependencies`
  so their install scripts deliberately never run.
- Migrations: Drizzle SQL generated by drizzle-kit and applied by Drizzle's
  migrator; a versioned TypeORM migration with `migrationsRun`; Prisma's
  committed migration SQL applied to a new file at startup (demonstration;
  `prisma migrate deploy` documented for deployments).
- `examples/orm-drizzle/tsconfig.json` sets `skipLibCheck` because drizzle-orm
  0.45 declarations do not type-check under TypeScript 6 (application code is
  still strict).

**Tests:** `tests/orm-examples.test.ts` (ports 4020-4022): boots each example
in-process against a fresh SQLite file; Live write + validation failure, action
write (client `author` ignored) and read, MVC read, wrong CSRF token, missing
Origin, invalid input (400 VALIDATION), Live snapshot replayed from another
session, persistence across restart. It also asserts the shared files are
identical and that **no package manifest under `packages/` depends on an ORM
or database driver**. Result: 5/5 pass.

**Docs:** each example README; `docs/guides/auth-and-data.md`; root README run
list and example table.

## DATA-015 / DATA-016: Passport/session/JWT patterns and optional auth starter

**Implemented** as `examples/auth-passport` (illustrative, clearly separated
from production identity configuration in its README):

- `@nestjs/passport` 12.0.1 + `passport` 0.7.0: `passport-local` 1.0.0
  strategy, `PassportSerializer` with express-session, `passport-jwt` 4.0.1 +
  `@nestjs/jwt` 12.0.4 (HS256 with explicit algorithms, issuer, audience,
  15-minute expiry). Password hashing `argon2` 0.45.2 (argon2id, OWASP
  parameters; prebuilt binary, install script not needed). No homegrown crypto:
  tokens are `crypto.randomBytes(32)`, stored as SHA-256 digests.
- Sign-in through `@nestvexa/forms` (`submitForm`: CSRF, Origin, validation)
  then the registered Passport strategy; `req.logIn` regenerates the session,
  CSRF is rotated; sign-out by POST with CSRF, `req.logOut` regenerates.
- Cookies: `HttpOnly`, `SameSite=Lax`, `Path=/`; with an https origin
  `Secure` and the `__Host-` prefix (`trustProxy` for TLS-terminating proxies).
- Registration with email verification, password reset (identical answer for
  unknown emails, 30-minute single-use links, new link revokes old ones, GET
  never consumes tokens, `Referrer-Policy: no-referrer`), all mail through
  `@nestvexa/mail` templates (`MemoryMailTransport` in tests).
- A password reset bumps the account's auth version, which the session
  deserializer and the JWT strategy check: every other session and JWT is
  revoked.
- Guards: `SignedInGuard`, `VerifiedGuard`, `RolesGuard` + `@Roles`,
  `CsrfGuard`, `AuthGuard('jwt')`, `AuthGuard('local')` for `POST /api/token`.
  Live `account-panel` re-reads `request.user` on every request; identity
  binding = user + auth version + session.

**Tests:** `tests/auth-passport.test.ts` (ports 4023, 4024): 12 tests covering
wrong/unknown credentials (one generic message), missing CSRF and foreign
Origin on sign-in, session regeneration on sign-in and sign-out (old id not
signed in), cookie attributes behind HTTPS, guest/member/admin and verified
guards, Live rename plus replay by another account, wrong CSRF header and dead
snapshot after sign-out, registration (weak password, duplicate email),
verification (CSRF required, single use, revoked on resend, expiry), reset (no
enumeration, expired, revoked, invalid, mismatched confirmation, missing CSRF,
reused token, sessions and JWTs revoked, old password refused), JWT API
(tampered, `alg: none`, wrong key, expired, wrong audience/issuer, stale auth
version, unknown subject, session cookie refused, member vs admin). Result:
12/12 pass.

**Docs:** `examples/auth-passport/README.md` (flows, authorization, production
identity checklist, OIDC recommendation), `docs/guides/auth-and-data.md`,
link from `docs/guides/forms.md`.

**Remaining gaps:** no throttling or lockout in the starter (documented;
`examples/auth-forms` has an in-memory throttle), no OIDC example (documented
as the recommended production path), in-memory session/user stores. Passport's
strategy registry is process-global, so one app instance per process (the test
starts its second instance last).

## DATA-017: consistent user context, server-side policy recheck

**Implemented as a host pattern** in `examples/multi-tenant/src/context.ts`:
one request context (session id, CSRF token, verified access to the active
tenant, binding `user:<id>:tenant:<slug>:role:<role>:session:<sid>`) from which
every transport's identity is derived: Live (`liveIdentity`), server actions
(`actionIdentity`), uploads (`uploadIdentity`), realtime (`realtimeIdentity` +
`authorizeChannel`), Inertia shared props (`sharedProps`), island props (page
tenant, signed) and MVC/REST (`TenantGuard`). Live authorization and realtime
channel policy re-check the binding against current memberships
(`currentMember`), not just parse it. `examples/auth-passport` shows the same
for Passport sessions (MVC + Live).

**Tests:** `tests/multi-tenant-isolation.test.ts` (cross-user cases on each
transport, see DATA-018) and `tests/auth-passport.test.ts` (Live user context).

**Remaining gap:** this is an example-level abstraction; there is no
framework-level user-context API in `packages/`. Another engineer (branch
`r5-kernel5`) is adding a kernel identity/tenant resolver; once merged, the
example's `context.ts` can be reduced to that API.

## DATA-018: multi-tenancy with server-side tenant resolution and isolation tests

**Implemented** by extending `examples/multi-tenant` (refactored into
`src/app.ts` `createApp()` + thin `src/main.ts`; default port 3119 unchanged):

- New transports: server actions (`workspace/projects`, `create`,
  `island-stats`), Inertia page `GET /t/:tenant/report` (`@nestvexa/inertia`,
  shared props from the context, no client bundle), signed island props
  (`@nestvexa/islands`, no client bundle; fallback text rendered), uploads
  (`@nestvexa/uploads`, `POST /t/:tenant/attachments`, per-tenant records),
  realtime (`@nestvexa/realtime`, one server-chosen channel per tenant, Live
  board subscribes via `@RealtimeChannels`), cache (`@nestvexa/cache`, tenant in
  the private key, tag invalidation on writes, guard before cache).
- Tenant comes only from a guarded route and the server-side session; actions
  refuse input where none is expected (`UNEXPECTED_INPUT`) and ignore a
  `tenant` field in inputs; Live components hold no tenant state.

**Tests:** `tests/multi-tenant-isolation.test.ts` (port 4026), 10 tests:
MVC/REST (guest, other tenant, spoofed query/header), Live (replay by another
tenant and by another user of the same tenant, forged `tenant` update, tenant
switch invalidates snapshots), Inertia (props scoped, shared user context,
403/303 for others), actions (smuggled tenant, no active tenant, another
session's CSRF, guest), islands (foreign signed props refused with
TENANT_MISMATCH, tampered with ISLAND_SIGNATURE), uploads (another tenant or
user cannot attach, wrong CSRF, tenant switch revokes, guest refused), realtime
(borrowed token refused for another tenant and another user, events delivered
to the tenant only, switch revokes), cache (per-tenant entry shared by members,
other tenant never served it, guard first, invalidation), member forging an
admin-only Live action. Result: 10/10 pass. The existing browser spec
`tests/browser/multi-tenant.spec.ts` still passes 7/7 in Chromium against the
extended example (local config, port 4027).

**Remaining gaps:** in-process realtime broker and cache store only (shared
stores documented); no subdomain tenant resolution or database row-level
security; island and Inertia page have no browser bundle in this example.
