# Risk register and recovery

P0 blocks all release candidates: exploitable cross-tenant data disclosure, arbitrary code execution, unauthorized mutations, secret leakage or destructive corruption. P1 blocks release: broken public contracts, missing mandatory feature, lifecycle leak, inaccessible primary flow or untested security control. P2 is a documented noncritical defect with a workaround; no blanket downgrade of unmet requirements is permitted.

## Recovery procedure

Preserve the master prompt and user files. Record checkpoints before tool/context interruptions. Re-run source-ledger checks after source changes; changed or removed tracked requirements require manual review so evidence is not silently reassigned. Keep generated outputs reproducible. Never erase a failing test, weaken a security assertion, disable a suite or mark a pending feature Done to make a release check green.

For test failures, capture the exact command/environment, make a targeted regression test where meaningful, fix and rerun the affected suite before expanding the matrix. For an incompatible dependency, pin a verified compatible release with a recorded rationale; do not force-install peers as a compatibility claim. For blocked infrastructure, keep local tests progressing and record precisely which service/browser/OS gate remains unrun.
